# netsafe → poisonguard：面向 AI 岗的项目重构方案

> 目标读者：面试官 / 你自己。读完这篇应该能回答三个问题——
> **这个项目原来为什么不可信？我改成了什么？为什么这套改法在本机（RTX 4060 Laptop 8GB / 16GB RAM）跑得动？**

---

## 0. 一句话结论

原项目是一个**看起来完整、实际自证循环**的演示：检测器是一张写死的关键词表，而"污染语料"正是用同一批关键词的模板生成的，所以"检测率接近 100%"不证明任何东西；更严重的是训练集和测试集是同一份数据，指标本身就不可信。

我把它重构成一个**三层检测框架**（数据层 / 行为层 / 语义层）+ 一条**可复现的评测流水线**，并把"检测率"换成投毒防御领域真正被认可的一组指标（TPR@FPR=1%、AUPRC、分家族召回、OOD 误报率、Bootstrap 置信区间、McNemar 显著性检验）。模型侧：本地 CoROM 句向量做数据层、已有 BERT 做行为层、**Qwen2.5-1.5B-Instruct + QLoRA** 做语义层判官，全部在 8GB 显存的笔记本上可训练可复现。

## 2. 十个硬问题：证据 → 后果 → 修法

| # | 问题 | 为什么致命 | v2 的修法 |
|---|---|---|---|
| 1 | **关键词循环论证** | 检测器和攻击样本共享词表，AUC 天然接近 1，等于自己给自己出题 | 攻击样本分四个能力递进的家族，其中 `paraphrase`/`subtle`/`backdoor` **刻意不含任何关键词**；关键词法降级为"弱基线"，用来被别的检测器打败 |
| 2 | **train = test** | 所有指标虚高，方法好坏无法比较 | 按**唯一文本**切 70/15/15，切分严格不相交；dev 与 test 的攻击样本再按内容哈希**分桶**，保证字符串级不相交 |
| 3 | **数据 75%+ 重复** | 模型只是在背 376 条模板，任何"检测"都是记忆 | 去重后再切分；报告里公开去重前后的对比数字 |
| 4 | **中文不分词** | KL 散度、TF-IDF、n-gram 全部失效 | 数据层改用**句向量**（CoROM/bge），距离在语义空间算，不依赖分词；需要词级特征时用字符 n-gram |
| 5 | **阈值拍脑袋（0.5）** | 分数分布未知，0.5 可能对应 40% 误报 | **在干净 dev 上按目标 FPR=1% 取分位数校准**，并报告实际达成的 FPR |
| 6 | **只有 accuracy** | 投毒检测是极不均衡任务，accuracy 可以被"全判正常"刷到 99% | 换 AUROC / AUPRC / **TPR@FPR=1%** / 分家族召回 / OOD 误报率 + Bootstrap CI + McNemar |
| 7 | **无验证集、无随机种子** | 结论不可复现，无法做模型选择 | 固定 seed、dev/test 隔离、所有曲线图可一键重跑 |
| 8 | **行为级检测是假实现**（KL/梯度范数随机数） | 论文里最核心的"行为偏移"根本没测 | 复用 `baseline_model.pth`，用**预测熵 / `p(poison)` / logit margin** 作为行为信号；再用线性探针做投毒比例消融 |
| 9 | **加密模型不可用** | 密钥丢失，文件是死重量 | 从流程里移除该文件（保留不动），改为"权重不加密、靠 `.gitignore` + 私有存储"的工程规范 |
| 10 | **元数据自相矛盾** | 注释写 `chinese_1b_model`/「10 亿参数」，实际 102M | 报告里的参数量、显存、耗时全部**由代码实测输出**，不手写 |

> 这十条里，第 1、2 条属于「结论不成立」，第 4、5、6 条属于「方法学不成立」，其余属于「工程质量」。
> 一个能过面试的改写，必须先把前两类修掉，再谈模型升级——**换更大的模型并不能救一个错误的实验设计**。

## 3. 为什么是「三层」，而不是「换个大模型」

单点检测必然有盲区，而且不同盲区需要不同层面解决：

```
                 ┌──────────────────────────────────────────┐
   训练数据 ───▶ │ 第 1 层 数据层（前置过滤，量大、必须便宜） │
                 │  句向量 + 距离/密度/孤立森林 + 融合       │
                 └───────────────┬──────────────────────────┘
                                 │ 灰区样本（占比小）
                                 ▼
                 ┌──────────────────────────────────────────┐
                 │ 第 2 层 语义层（判断"这句话是否真的有害"） │
                 │  Qwen2.5-Instruct 判官 / QLoRA 微调版     │
                 └───────────────┬──────────────────────────┘
                                 │ 落库训练
                                 ▼
                 ┌──────────────────────────────────────────┐
                 │ 第 3 层 行为层（上线后监控模型是否被带偏） │
                 │  受害模型熵 / p(poison) / 探针 + 触发词扫描│
                 └──────────────────────────────────────────┘
```

**每一层都有明确的失败模式，也就能解释"为什么需要下一层"：**

| 层 | 能抓 | 抓不到 | 成本 |
|---|---|---|---|
| 数据层 | 模板残留、语义漂移、离群簇 | 与正常文本同分布的 backdoor（内容是正常句子 + 触发词） | 一次编码 ~0.06s/条（CPU，25 字） |
| 语义层 | subtle 事实错误、paraphrase 换词 | 大规模数据（每条都要过 LLM） | CPU 0.5B ≈ 1~3s/条；GPU 1.5B ≈ 0.2s/条 |
| 行为层 | backdoor（模型对触发词异常自信）、整体偏移 | 少量、未激活的投毒 | 一次前向，无需额外模型 |

这正是「级联（cascade）」的工程动机：**便宜的先跑，贵的只看灰区**。CLI 里的 `score_cascade()` 就是这一实现，报告里会给出"实际调用 LLM 的比例"。

## 4. v2 目录结构

```
netsafe/
├── poisonguard/                  # 新实现（可 pip 安装的包）
│   ├── config.py                 # dataclass 配置 + YAML 覆盖
│   ├── data.py                   # 去重 → 分层切分 → 攻击注入
│   ├── attacks.py                # 4 个攻击家族（含分桶去重，保证 dev/test 字符串不相交）
│   ├── encoders.py               # CoROM / bge / Qwen3-Embedding 句向量 + 缓存
│   ├── localmodels.py            # 本地模型定位 + ModelScope 下载（HF 不可达）
│   ├── detectors.py              # keyword/centroid/knn/mahalanobis/iforest/fusion + 阈值校准
│   ├── victim.py                 # 行为层：BERT 熵 / p(poison) / 线性探针
│   ├── judge.py                  # 语义层：Qwen 判官（零样本/少样本/级联/缓存）
│   ├── train_qwen_lora.py        # QLoRA 微调判官（手写训练循环，少依赖）
│   ├── evaluate.py               # 指标 + 图表
│   ├── report.py                 # 自动生成 Markdown 实验报告
│   └── cli.py                    # data/detect/victim/judge/ablation/report/all
├── configs/default.yaml
├── data/raw/                     # 原 CSV（只读）
├── data/processed/               # 切分后的 jsonl（可重建）
├── legacy/                       # 原 3 个脚本 + 问题说明（对照用，不再维护）
├── docs/优化方案.md              # 本文
├── docs/实验报告.md              # 自动生成，所有数字来自 metrics/*.json
├── outputs/{cache,metrics,figures}/
└── tests/                        # 单测（数据切分不泄漏、阈值校准、指标正确性）
```

设计取舍一句话总结：**`legacy/` 保留原代码作为「问题证据」，新实现放在 `poisonguard/` 且每个模块只有 100~300 行、单一职责**——面试时任何一行都能讲清楚，不会出现"862 行的文件里 90% 是死代码"这种局面。

## 5. 模型选型

### 5.1 句向量编码器（数据层）

| 候选 | 参数量 | 维度 | 权重体积 | 本机实测 | 结论 |
|---|---|---|---|---|---|
| **CoROM-base**（`damo/nlp_corom_sentence-embedding_chinese-base`） | 102M | 768 | 390MB | **已在本机 `model_cache/`，离线可用** | ✅ 默认 |
| bge-small-zh-v1.5 | 24M | 512 | 95MB | 需下载 95MB（ModelScope 可达） | 备选：快 4 倍，显存 0.2GB |
| Qwen3-Embedding-0.6B | 595M | 1024 | 1.2GB | 需下载；GPU 更合适 | 备选：效果最好，成本最高 |

选 CoROM 的理由很实际：**它已经在仓库里了**（原项目 `modaldown.py` 下载的就是它），复用等于零下载成本、零网络风险；且 768 维在 3000 条样本上跑 kNN/马氏距离完全够。

### 5.2 判官（语义层）

| 候选 | 4bit 权重 | 8GB 显存 | CPU 可行性 | 选择 |
|---|---|---|---|---|
| **Qwen2.5-1.5B-Instruct** | ~1.0GB | ✅ 余量充足 | 慢（~2s/条）但能跑 | ✅ 主选 |
| Qwen2.5-0.5B-Instruct | ~0.35GB | ✅ | ✅ ~0.5s/条 | 备选：CPU 冒烟 / 显存告急 |
| Qwen2.5-3B-Instruct | ~1.9GB | ⚠️ 训练时激活吃紧 | ❌ | 不选 |
| Qwen2.5-7B-Instruct | ~4.4GB | ❌ 训练必 OOM | ❌ | 不选（推理勉强） |

**为什么不是 7B：** 1.5B 的 QLoRA 训练显存 ≈ 4.1GB（见下表），7B 光 4bit 权重就 4.4GB，加上激活/优化器要 10GB+，8GB 卡必然 OOM。硬上只能做推理不能微调，而"能微调"本身就是这个项目要展示的能力。

**为什么不是全参数微调：** 1.5B 全参训练需要 权重(3GB bf16) + 梯度(3GB) + Adam 动量(6GB) ≈ 12GB，直接出局。LoRA 只训练 ~0.2% 参数（r=8 时约 4.2M），把优化器状态从 GB 级压到 MB 级。

**为什么是 Instruct 而不是 Base：** 判官任务需要遵循"只输出 JSON"的指令，Instruct 版零样本就能用，微调只是把领域偏好（subtle 家族的识别）注进去，样本量 300~800 条即可，不需要重学指令跟随。

**本机实测（0.5B 已真跑，不是估计值）：**

| 项目 | 实测值 |
|---|---|
| 权重落盘 | 988MB（`model_cache/Qwen/Qwen2___5-0___5B-Instruct/`） |
| CPU 逐条推理 | **1.39 s/条**（240 条 384s，few-shot 4 例，max_new_tokens=48） |
| 240 条抽样（每家族/干净各 40） | AUROC 0.706 / P 0.826 / R 0.713 / F1 0.765 / **FPR 0.300** |
| 分家族召回 | template 100% / paraphrase 87.5% / subtle 85.0% / **backdoor 12.5%** |
| 二值输出 ⇒ TPR@1% | **0.000**（1% 误报预算下切不出工作点） |
| 级联（kNN 闸门，q80~q99.5） | 只有 19.4% 进 LLM，召回反而掉到 16.7% |

**Prompt 敏感性（同一个模型、10 条手写对照样本，脚本 `outputs/cache/_promptcmp.py`）：**

| 变体 | 准确率 | 现象 |
|---|---|---|
| few-shot 4 例（当前） | **9/10** | 唯一漏的是"内部消息称…本条已核实"这种 backdoor 式句子 |
| 零样本 | 6/10 | 复读标准："无明显危害、违法或明显伤害健康的操作指导"——把判定标准当理由吐回来 |
| 零样本 + 追加"该剔除吗" | 5/10 | 全军覆没成"污染"，把"提到医生"也当违规 |
| one-shot 单正单负 | 6/10 | 短上下文反而更爱复读示例 |
| 零样本 + assistant 预填 `{"label": "` | 6/10 | 格式对了但判断仍乱 |

结论写进代码注释了：**小模型的指令跟随比大模型脆，prompt 必须在同型号上实测**。这也直接决定了两条改进方向（v3 第一优先）：
①判定接口从"让模型吐 JSON"改成"给 `污染`/`正常` 两个 token 取 logprob 做打分"——天然连续、可校准、可算 AUROC，不再受二值输出卡死；
②闸门换成有监督分并把"自动判干净"的门槛压到低分位——级联能不能省成本取决于第一级**召回**，不是准确率。

### 5.3 显存预算（实测/推算，RTX 4060 Laptop 8GB）

| 阶段 | 组成 | 占用 |
|---|---|---|
| QLoRA 微调 1.5B | 4bit 权重 1.0 + LoRA+优化器 0.1 + 激活(seq512,bs2) 2.0 + CUDA context 1.0 | **≈ 4.1GB** ✅ |
| 1.5B 4bit 推理（判官） | 权重 1.0 + KV cache(bs8) 0.6 | **≈ 1.6GB** ✅ |
| CoROM 编码（GPU） | 权重 0.4 + 激活 0.5 | **≈ 0.9GB** ✅ |
| bge-small 编码 | 0.1 + 0.3 | **≈ 0.4GB** ✅ |
| ~~7B 4bit 微调~~ | 权重 4.4 + 激活 3.5 + 优化器 0.6 | **≈ 8.5GB** ❌ OOM |

> 关键工程手段（都写在 `train_qwen_lora.py` 里）：`load_in_4bit`(nf4 + double quant) → 权重四分之一；`gradient_checkpointing` → 激活再降 50~70%；`bs=2 × grad_accum=8` → 等效 batch 16 但峰值不变。

## 6. 本机可行性：分阶段路线（每步都有明确产出与回退）

本机实测：**torch 2.9.1 是 CPU 版**（`cuda_available=False`），CUDA 12.7 驱动就绪但没装 CUDA 版 torch。因此路线分两条：

### 路线 A：CPU（默认，不装任何新东西就能跑完）

| # | 阶段 | 命令 | 耗时（实测/估算） | 产出 |
|---|---|---|---|---|
| 1 | 数据 | `python -m poisonguard.cli data` | **0.2s** | `data/processed/*.jsonl`、去重统计 |
| 2 | 数据层检测 | `python -m poisonguard.cli detect` | 编码 8.6k 条 **≈ 8.5 分钟**（实测 17 条/s）+ 拟合 <10s | ROC/家族热力图、`detect.json` |
| 3 | 行为层 | `python -m poisonguard.cli victim` | BERT-base 8.6k 条 ≈ 3~5 分钟 | `victim.json`、行为信号 ROC |
| 4 | 比例消融 | `python -m poisonguard.cli ablation` | ≈ 2 分钟 | `ablation.json`、消融曲线 |
| 5 | 语义层（需先下 0.5B） | `python -m poisonguard.cli judge --limit 40 --qwen-model 0.5b` | **实测 433s**（240 条判定 384s + 180 条级联抽样） | `judge.json`、判官 ROC |
| 6 | 报告 | `python -m poisonguard.cli report` | 1s | `docs/实验报告.md` |

不含语义层约 **15 分钟**，加上 Qwen 0.5B 判官约 **22 分钟**；16GB 内存够（峰值 <4GB）。这是"能当场演示"的路径。

> CPU 上跑 LLM 的三个工程细节（都在代码里）：①按 `--judge-chunk 24` 分块推理并逐块 flush 判定缓存，中断后重跑能续上；②缓存键是文本 sha1，同一句话不会推理两次；③`--cascade-max` 把级联抽样到 180 条，否则灰区 600 条要多等 14 分钟。

### 路线 B：GPU（想展示微调能力时）

| # | 步骤 | 命令 | 说明 |
|---|---|---|---|
| 0 | 换 CUDA 版 torch | `pip install torch --index-url https://download.pytorch.org/whl/cu126` | ~3GB，**会覆盖现有 CPU 版**；建议在独立 venv 里做 |
| 1 | 装训练依赖 | `pip install peft accelerate bitsandbytes datasets` | Windows 上 bitsandbytes 4bit 支持有限，可 `--no-4bit` |
| 2 | 下载 Qwen | `python -m poisonguard.cli download --qwen 1.5b` | 走 ModelScope（HF 在本机不可达） |
| 3 | 微调 | `python -m poisonguard.train_qwen_lora --max-steps 200` | 4060 上 ≈ 6~10 分钟 |
| 4 | 评测 | `python -m poisonguard.train_qwen_lora --eval-only --adapter outputs/qwen/lora-adapter` | 与零样本判官同口径对比 |
| 5 | 级联实验 | `python -m poisonguard.cli judge` | 统计"只有多少比例样本真正调用了 LLM" |

> 我不想偷偷替你动全局环境：`pip install torch --index-url .../cu126` 会把 3GB 的 CPU 版覆盖掉，而且可能与已装的 torchvision/torchaudio 版本冲突。**这一步留给你在 venv 里执行**，命令已经写进 README 和本文。
> 加 `--allow-cpu` 也能在 CPU 上跑通 `train_qwen_lora.py` 的完整训练循环（1.5B、200 步，约 1~2 小时），用于验证脚本正确性。

### 踩坑清单：本机真撞上的 6 个问题（都已修，多数写进了测试）

这些是"文档里看不到、真跑才会撞上"的问题，也是我觉得比模型选型更能体现工程能力的地方：

| 坑 | 现象 | 根因 | 修法 |
|---|---|---|---|

### 失败回退链
`Qwen 1.5B 微调 OOM` → `--no-4bit` 关量化会更糟，正确做法是 `seq_len 512→256`、`bs 2→1`、或退到 `0.5B`；
`Qwen 权重下载失败` → 判官自动降级为 `judge_heuristic`（报告中明确标注为 fallback，不混进主结论表）；
`GPU 不可用` → 全流程 CPU 照常，只是慢。

## 7. 评测协议：为什么这些指标，而不是 accuracy

1. **TPR@FPR=1%**：真实运维里误报直接等于人工成本，所以阈值必须按误报率定，不能按"分数 0.5"定。报告里每个检测器都用**干净 dev 的分位数**校准，再在 test 上固定该阈值评估。
2. **AUPRC + AUROC**：AUPRC 对正类比例敏感（本项目 test 正类 61%，若换成真实场景 0.1% 会完全不同），所以两个都报，并说明差异。
3. **分家族召回**：这是最有信息量的表。如果某检测器 `template` 上 0.99、`paraphrase` 上 0.2，说明它学的是"关键词"而不是"有害性"——这正好能量化原项目那个关键词检测器的真实水平。
4. **OOD 误报率**：干净 test 里混了 500 条分布外正常文本（生活类，句式与训练集不同），专门测"检测器是否把没见过的话题判成投毒"。这是投毒检测最容易翻车的地方。
5. **Bootstrap 95% CI**：500~2000 条正类的 AUROC 差别常常在噪声内，不给区间就是在比噪声。
6. **McNemar 检验**：逐样本配对比较，回答"融合检测器比 kNN 好，是真的好还是碰巧"。
7. **dev/test 字符串级不相交**：只换随机种子不够（`subtle` 家族模板只有 300 种组合，换种子仍会大面积重叠），所以额外按内容 CRC32 分桶，`dev` 取 bucket 0、`test` 取 bucket 1。

## 8. 三个把漂亮数字打回原形的实验（v2.1）

做完全流程后 `sup_tfidf` 拿到 AUROC 1.000、TPR@1% 1.000。这种满分在投毒检测里几乎一定是评测出了问题。我先怀疑"dev/test 共享模板骨架"，于是加了模板留出（`--style-holdout`，dev 用模板折 0、test 用模板折 1，两折交集为空）：

| 检测器 | 宽松口径 AUROC | 模板留出 AUROC |
|---|---|---|
| knn | 0.997 | 0.997 |
| mahalanobis | 0.996 | 0.996 |
| sup_lr | 0.920 | 0.895 |
| sup_tfidf | 1.000 | 0.997 |

**几乎没变。** 所以模板泄漏不是主因。真正的原因在干净语料：`normal_data_2w.csv` 根本不是自然语言，而是 `10 主题 × 10 方面 × 10 领域` 的槽位拼句机——去重后 4997 条，字符 2-3gram 词表**只有 994 个**。任何稍微像人话的句子对它都是"分布外"。

于是补了三个实验，全部进了 CLI：

**① 换真实干净侧（`download --corpus tnews` + `--clean-source tnews`）**
用 CLUE/tnews 的 19,265 条真实新闻标题替换干净语料，攻击不变：

| 检测器 | 合成干净侧 AUROC | 真实干净侧 AUROC |
|---|---|---|
| knn | 0.997 | **0.428** |
| mahalanobis | 0.996 | 0.599 |
| iforest | 0.902 | 0.726 |
| sup_lr | 0.920 | 0.911 |
| sup_tfidf | 1.000 | 1.000 |

`knn` 掉到 0.428 < 0.5：**排序方向反了**。真实新闻足够多元，离训练质心比合成的攻击句更远。无监督离群检测的隐含前提「离群 = 有害」在真实语料上不成立——这不是调参问题，是前提问题。

**② 词面审计（`audit`）**
用与 `sup_tfidf` 完全相同的配置在 dev 上拟合，统计有多少决策权重落在"干净语料里从未出现过的 n-gram"上：

| 干净语料 | 干净侧 n-gram 词表 | OOV n-gram 占比 | 它们占决策权重 |
|---|---|---|---|
| 合成槽位语料 | 994 | 85.8% | **49.2%** |
| 真实新闻语料 | 336,645 | 27.8% | 35.6% |

合成基准上的近一半权重来自"没见过这种句式"。这就是满分的来源。

**③ 硬负样本（`hardneg`）**
从真实新闻里筛 309 条含「内部/据知情/透露/通报/统计/流出/截图/调查」等措辞、但完全无害的句子，与攻击混在一起比：

| 检测器 | 攻击 vs 硬负样本 AUROC |
|---|---|
| knn | 0.500 |
| mahalanobis | 0.581 |
| sup_tfidf | 1.000 |

`knn` 等于抛硬币；`sup_tfidf` 仍 1.000，但结合 ② 可知它认的是**合成攻击的固定措辞骨架**，换个模板就失效。

### 这一节真正想证明的东西

不是"我的检测器多强"，而是：**我能把自己的指标拆开、找到虚高的来源，并把它量化成可复现的实验。** 面试里这比多两个百分点的 AUROC 值钱——因为绝大多数人只会报最好看的那个数。

对应地，我把结论也写进了 README 和实验报告的"局限"章节：`sup_tfidf` 的 1.000 **不应被解读为"能识别有害性"**。

**面试讲解脚本（3 分钟版）**

> "这个项目最初是一个中文训练数据投毒检测的 demo，我接手时它的问题不是效果差，而是**结论不成立**：检测器是关键词表，污染样本又是用同一批关键词的模板生成的，等于自己出题自己判卷；而且训练集和测试集是同一份数据。我做的第一件事是**证伪**——统计出去重后只剩 4997 / 376 条唯一文本，把 train=test 的泄漏指出来，并写了 `legacy/README.md` 留证据。
>
> 第二件事是重建评测：攻击样本拆成四个能力递进的家族，其中三个刻意不含关键词；阈值改成按干净 dev 上 1% 误报校准；指标换成 TPR@FPR=1%、AUPRC、分家族召回、OOD 误报，加上 Bootstrap 区间和 McNemar 检验。
>
> 第三件事是分层：数据层用句向量做便宜的全量过滤，语义层用 Qwen 判官只处理灰区，行为层用受害模型的熵/置信度抓 backdoor。判官我真的在本机跑起来了——0.5B、CPU、240 条实测，AUROC 0.706、`backdoor` 只召回 12.5%，而这个 12.5% 恰好证明"语义层看不见后门"，三层是各补一个洞。顺带我还测了 prompt 敏感性：同一个模型 few-shot 能到 9/10，去掉示例就掉到 6/10，所以这类小模型的 prompt 必须同型号实测。整个流水线在这台笔记本上 CPU 15 分钟跑完，能当场复现；1.5B + QLoRA 的脚本也写好了，只是要 GPU，命令在 README 里。"

**如果被追问的四个硬问题**

1. *"你的攻击样本是程序生成的，有说服力吗？"*
   → 承认这是局限（报告第 8 节明写；第 8 节还给了量化：模板留出后仍是 0.997，说明问题不在模板，而在合成攻击与真实语料之间的词面鸿沟）。生成式攻击的价值在于**可控消融**：能精确隔离"攻击是否含关键词""是否改变事实"这些因素。真实数据上的验证是下一步，已列进 roadmap。
2. *"为什么不用更大模型？"*
   → 不是不想，是边界：8GB 显存下 7B 的 QLoRA 必然 OOM；而 1.5B 微调后在本任务上（二分类 + 结构化输出）已经够用，判官的任务复杂度远低于通用对话。省下来的算力用在"多家族评测 + 统计检验"上，收益更高。
3. *"你的受害模型权重是别人训的，可信吗？"*
   → 不可信，所以只用相对信号（同模型内不同样本的排序），不引用它的绝对准确率，并在报告里显式声明。这正是"知道自己的实验边界在哪"。
4. *"你的判官 AUROC 才 0.706，是不是说明 LLM 这条路走不通？"*
   → 恰好相反，它说明我是在**最小可用配置**下把这条路走通的，并且知道瓶颈在哪。三个具体原因：①模型是 0.5B（8GB 显存 + CPU 推理的下限）；②判定接口是"吐 JSON"，输出二值，`TPR@1%` 结构性为 0；③级联闸门用 kNN，把真阳性挡在门外。三条改进都写进了 roadmap：换 logprob 打分（不改模型只改接口）、闸门换成有监督分并压低"自动判干净"的分位、上 1.5B + QLoRA。更重要的是，**一个我自己跑出来、并且能解释清楚的 0.706，比一个来路不明的 0.99 更有说服力**。

## 11. 后续路线（下一步做什么）

第 8 节的三个实验把路线图的优先级重排了：**先修评测，再堆模型。**

**v3 第一优先（直接针对第 8 节暴露的问题）**

1. **真实攻击集**：现在攻击是合成的，干净侧换成真实新闻后仍能 100% 分开，说明「合成攻击 vs 任何语料」这个二分类本身太容易。下一步做「真实新闻 + 最小编辑式篡改」——在真实无害新闻上做单点替换（把"某地发生地震"改成"某地发生爆炸且无人伤亡"），只改事实不改文风。这样检测器才必须读懂内容。
2. **把硬负样本升级为主评测集**：让"像传闻的无害新闻"成为默认对手而不是压力测试，指标从"能否分开合成攻击"改为"能否在同样措辞下分开真假"。
3. **给 `sup_tfidf` 重新定位**：不再作为"最强检测器"报告，而作为**数据自然度的偏差探测器**保留——它的 OOV 权重占比（`audit` 的 49.2%）就是"这批数据有多不自然"的度量。

**v3 第二优先（能力扩展）**

4. **判官的判定接口换成 logprob 打分**：现在它吐 JSON、输出二值，在 1% 误报预算下 `TPR@1%` 直接是 0（见 §5.2 实测）。改成读 `污染`/`正常` 两个 token 的 logprob 后，分数天然连续、可校准、能算 AUROC——这一步不改模型只改接口，收益最大。
5. **级联闸门重做**：把闸门从 kNN 换成有监督分，并把「自动判干净」的分位从 q80 压到 q20~q30，让 LLM 只看中段。本机实测旧闸门 19.4% 调用率、召回 16.7%，说明省成本的前提是闸门高召回。
6. **攻击更强**：加 GCG 风格后缀攻击、同义改写、字符级混淆（拼音/火星文），检验检测器是否还是"表面特征依赖"。
7. **去重与相似度作为防线**：投毒常常伴随"高重复 + 高相似"，把 MinHash/SimHash 去重纳入流水线（本项目的重复率统计已经证明这条线索有效）。
8. **在线监控**：把行为层信号（熵、p(poison)、触发词命中）做成滑动窗口指标 + 告警阈值，而不是离线跑一次。
9. **判官蒸馏**：把 1.5B 判官蒸馏到 bge + 分类头（~25M），把单条成本从 200ms 降到 1ms，用于全量数据。
10. **红队流程化**：把四个攻击家族包装成"上线前必跑的红队套件"，纳入 CI（小样本冒烟）。

## 12. 局限（主动声明）

1. 攻击样本由模板/参数化生成，覆盖不了真实对抗者的全部手法；`subtle` 家族模板组合空间有限（约 300 种固定句式 + 参数化扩展），已用分桶保证 dev/test 不相交，但仍属同分布攻击。
2. **真实语料基准只替换了干净侧**，攻击仍是合成文本。它证明的是"干净侧越贫瘠、虚高越多"，不是真实场景的绝对检出率（第 8 节已量化）。
3. **`sup_tfidf` 的 1.000 是偏差，不是能力**：词面审计显示合成基准上近一半决策权重来自干净语料里没出现过的 n-gram，硬负样本实验也给出它会认"措辞骨架"的证据。该数字不得解读为"能识别有害性"。
4. 受害模型 `baseline_model.pth` 的训练数据存在 train=test 泄漏，本项目只用其相对信号。
5. 投毒比例消融用线性探针替代 BERT 全量重训（成本-精度权衡，规律可迁移，绝对值不可直接引用）。
6. QLoRA 微调的判官效果依赖样本量与标注质量，本项目用 dev 集的程序化标注，未做人工复核。
7. **语义层只在 Qwen2.5-0.5B + CPU 上实测**（240 条抽样、1.39s/条）。1.5B 零样本与 QLoRA 微调的对比需要 GPU：脚本（`train_qwen_lora.py`）已就绪、命令写在 README，但本机未跑。所以 §5.2 那张表的绝对数值应读作"最小可用模型的下限"，而不是这套方法的天花板。
8. 本机 torch 为 CPU 版，GPU 路线的耗时数字来自显存预算推算而非实测（CPU 路线耗时是实测值）。
