# 多实例部署

> 方向③ 在线 API 服务 —— 缺口5：多实例部署文档。
> 面向"单机 `python -m poisonguard.cli serve` 已经能跑，但要扛量/扛故障"的阶段。

## 1. 先说清现状

`serve` 是**有状态外壳 + 无状态打分内核**：

| 部分 | 状态 | 多实例含义 |
| --- | --- | --- |
| 打分链路（`/score`，kNN + n-gram + 学生） | **无状态**（数据只读，纯 CPU 计算） | 可随意水平扩展，副本之间互不依赖 |
| `/health` `/stats` `/metrics` | 每实例自报 | 负载均衡 + 监控各抓各的 |
| 鉴权（API Key）、限流（令牌桶） | **进程内**（`security.py` RateLimiter 每实例独立） | 多实例下限流是"每实例每 key"而非全局；要全局配额得在上游（网关/Redis）做 |
| 审计日志（sqlite） | **进程内写文件** | 默认 `outputs/audit/audit.sqlite3`，多实例共享同一文件会并发写 → SQLite 锁竞争 |
| 异步批处理（`/batch`） | **进程内队列 + 线程池**（`service.py` `_batch`/`_executor`） | **job 只在提交它的那个实例里存在**：轮询必须打到同一实例（会话亲和），或上外部队列 |
| 模型版本注册表/热更新（`/admin/*`） | **进程内**（`_versions`/`_active`） | reload/switch 只影响被调用的那个实例 |

**结论**：
- `/score`（同步在线打分）是**天然可水平扩展**的部分 —— 这才是多实例的主战场。
- `/batch`、`/admin/*`、审计写库这些**进程内状态**在多实例下要么"亲和到单实例"，要么"升级成外部组件"。下面给两条现实路线。

## 2. 目标架构

```
                    ┌──────────────────────────────────────┐
                    │  网关（Nginx / HAProxy / CLB）        │
                    │  · TLS 终结  · 4层/7层 LB             │
                    │  · 可选：全局限流（Redis/漏桶）       │
                    └──────────────┬───────────────────────┘
                 round-robin 打到任意副本（/score 无状态）
        ┌──────────────┬───────────┼──────────────┬──────────────┐
        ▼              ▼           ▼              ▼              ▼
   ┌─────────┐   ┌─────────┐  ┌─────────┐   ┌─────────┐    ┌─────────┐
   │ serve:1 │   │ serve:2 │  │ serve:3 │...│ serve:N │    │ (可选)  │
   │ :8000    │   │ :8000    │  │ :8000    │   │ :8000    │    │ admin-  │
   │          │   │          │  │          │   │          │    │ node    │
   └────┬──────┘  └────┬──────┘  └────┬──────┘   └────┬──────┘  └────┬───┘
        │              │              │               │              │
        ▼              ▼              ▼               ▼              ▼
   ┌────────────────────────────────────────────────────────────────────┐
   │   只读挂载：data/</后缀>/processed + outputs/metrics/student.pkl     │
   │   （配方/阈值/学生模型三样在所有副本必须一致）                       │
   └────────────────────────────────────────────────────────────────────┘
        │              │              │               │              │
        ▼──────────────────────────────────────────────▼
   Prometheus scrape 各副本 /metrics（admin key 抓） → Grafana
   审计：N 份独立 sqlite（每副本）或汇聚到共享库（下详）
```

### 2.1 副本之间的"一致三件套"

多实例**最危险的坑**是副本间模型不一致（A 副本阈值 0.5、B 副本 0.05，同一个文本两个结果）。
上线前必须保证三样完全一致：

1. `configs/default.yaml`（含 `detector.target_fpr` 等阈值口径参数）；
2. `data/processed<后缀>/` 的干净 dev 集（`resolve_threshold` 按它标定阈值）；
3. `outputs/metrics/student_judge<后缀>.pkl`（蒸馏学生模型）。

> 版本固化做法：把这三样打成**不可变发布包**（tar 或容器镜像分层），用同一 tag 起所有副本；
> 不要每副本手改配置。`deploy.py` 的 `DeployedScorer.version` 会带 `pkg-vN/域`，
> 配合 `/health` 的 `model` 字段做启动校验：**所有副本 health 的 model 必须一致**再接入 LB。

## 3. 路线 A：无状态化水平扩展（推荐，覆盖 95% 场景）

适用于"在线打分量大但批处理量小/可接受亲和"的现实。原则：** `/score` 无状态可任意打，`/batch` 和 `/admin` 只放在 admin-node**。

### 3.1 本机/单机多 worker（最简单的多实例）

```bash
# uvicorn 多 worker：注意 worker 数 < CPU 核数，编码器每个 worker 各加载一份
python -m uvicorn poisonguard.service:create_app --factory \
    --workers 4 --host 0.0.0.0 --port 8000
```

> 说明：`--factory` 会调用 `create_app()`；`create_app(cfg=None)` 默认 `load_config(None)`。
> 若要走 CLI 的 `--config/--student/--api-key/--audit` 全套参数，推荐用前置脚本（见 3.3 的 entry.sh）。

### 3.2 Docker Compose 多副本 + 负载均衡

写好这两个文件后 `docker compose up -d --scale serve=4`。

**docker-compose.yml**：

```yaml
services:
  serve:
    build: .
    image: poisonguard:latest
    # 无状态打分副本：不挂审计、不开 admin（不给 admin-key）
    command: >-
      serve --host 0.0.0.0 --port 8000
      --api-key ${SERVE_API_KEY}
      --admin-key ${ADMIN_API_KEY}
      --audit /tmp/audit/audit.sqlite3
    environment:
      POISONGUARD_LOG_LEVEL: INFO
    volumes:
      # 只读共享"一致三件套"（模型缓存也要共享，避免每副本各拉 400MB 编码器）
      - model_cache:/app/model_cache:ro
      - ./configs:/app/configs:ro
      - ./data:/app/data:ro
      - ./outputs:/app/outputs:ro
      - audit_tmp:/tmp/audit   # 每副本独立卷，审计各写各的
    deploy:
      replicas: 4
      resources:
        limits: { cpus: "2.0", memory: 4g }

  lb:
    image: nginx:alpine
    ports: ["8000:80"]
    volumes:
      - ./deploy/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on: [serve]

volumes:
  model_cache:
  audit_tmp:
```

**deploy/nginx.conf**（7 层反代 + 会话亲和给 `/batch` + 摘流式的健康检查）：

```nginx
upstream poisonguard {
    # /score 走轮询（无状态）
    server serve:8000;
    server serve:8000;
    server serve:8000;
    server serve:8000;
}

server {
    listen 80;
    location /health {
        # 健康检查只给 LB 用：不给 key 也能探（鉴权默认关则 200）
        proxy_pass http://poisonguard;
    }
    location /batch/ {
        # 批处理队列在提交实例里 → 会话亲和（sticky），保证轮询打到同一副本
        proxy_pass http://poisonguard;
        sticky cookie srv_id expires=1h;
    }
    location / {
        proxy_pass http://poisonguard;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

> **批处理亲和边界**：`sticky` 只保证"同一客户端会话"亲和一个副本。
> 若 client 会在不同连接间轮询 job，必须在应用层把 `job_id -> 副本` 路由做进网关，
> 或按 **路线 B** 升级为外部队列。演示/内网用量下 sticky 够用。

### 3.3 启动入口脚本（推荐封装）

CLI 的 `serve` 子命令参数很多，多副本部署建议统一入口脚本 `deploy/entry.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail
# 每次启动先自检一致性：model 版本/阈值必须与发布 tag 相符（fail-fast 别再接入 LB）
exec python -m poisonguard.cli serve \
  --host 0.0.0.0 --port 8000 \
  --config "$POISONGUARD_CONFIG" \
  --student "$POISONGUARD_STUDENT" \
  --api-key "$SERVE_API_KEY" \
  --admin-key "${ADMIN_API_KEY:-}" \
  --audit "${AUDIT_PATH:-/tmp/audit/audit.sqlite3}"
```

又因为 `create_app` 支持 `security=` 注入，自检也可以写成一个薄启动器：

```python
# deploy/run.py —— 比 shell 更可控：启动前校验 model_info 一致，再 uvicorn.run
from poisonguard.config import load_config
from poisonguard.service import create_app

cfg = load_config("configs/default.yaml")
app = create_app(cfg, student_path="outputs/metrics/student_judge_real_v3.pkl")
if __name__ == "__main__":
    import uvicorn
    uvicorn.run(app, host="0.0.0.0", port=8000)
```

## 4. 路线 B：批处理上外部队列（真正"多实例共享批处理"）

进程内 `_batch` 的局限在多实例下会放大：
- job 驻留内存（默认 128 job），副本各自 128，总量不可控；
- worker 线程池每副本 2 个，横向扩容 = 队尾并行度线性涨，**没有全局公平**。

升级路径（按成本从低到高）：

1. **只读共享 + 每副本独立队列**：维持现状，靠 Nginx sticky 亲和。成本 0，够内网。
2. **Redis 队列**：把 `POST /batch` 变成 `LPUSH job_queue {texts…}`，任一 worker 实例 `BRPOP` 执行；
   job 结果写 Redis（`HSET job:{id} state results`），`GET /batch/{id}` 读 Redis —— 真正的"谁都能提交、谁都能查"。
   `service.py` 的 `_batch_*` 与 `_run()` 是可替换点，接口契约不变（`POST /batch` → `{job_id,status,total}`，
   `GET /batch/{id}` → `{job_id,state,total,done,results}`），把实现换掉即可，网关不再需要 sticky。
   Redis 里的 job 过期策略（如 24h TTL）替代进程内 128 上限淘汰。
3. **任务队列 + 持久化**（Celery/RQ + RabbitMQ/PostgreSQL）：要排队语义、重试、优先级时上。

> 我们这版交付的是**进程内实现 + 接口契约**；外部队列是替换实现、不改契约的演进，
> 因此契约测试（`tests/test_batch.py`）在两条路线上都成立。

## 5. 管理端点（/admin/*）在多实例下的正确姿势

热更新/版本切换是**进程内**状态，多实例下**不要**对 LB 后面所有副本都暴露 `--admin-key`：

- **推荐**：只在一个"管理节点"（admin-node，默认不接入 LB 流量）开 `--admin-key`。
  发布流程变成：
  1. 新三件套（配置/数据/学生）推到共享只读卷，做成版本 tag；
  2. **滚动**：对 LB 摘掉副本 i 的流量 → 重启副本 i（加载新 tag）→ 校验 `/health` model → 重新接入 → i+1；
  3. 全员就绪后再对 admin-node `POST /admin/reload` 让它和副本对齐（或干脆 admin-node 也走重启）。
- 如果非要"一键全量 reload"：所有实例配**同一把** admin key，对每个实例依次调
  `POST /admin/reload`（串行，别并发，避免瞬时两套阈值并存）。
- `/admin/rollback` 同样按实例操作；**reload 失败时服务会 500 且保持旧模型**（契约已测），
  多实例下配合摘流重试即可，不必全局回滚大动干戈。

## 6. 监控与告警（配合缺口4 `/metrics`）

- **抓取**：Prometheus 配置多个 static target（或 file_sd/consul_sd），每副本一个
  `http://serve:8000/metrics`，抓取时带 `X-API-Key: $SERVE_API_KEY`（若开了鉴权）。
  Docker Compose 示例：

```yaml
# prometheus/prometheus.yml（片段）
scrape_configs:
  - job_name: poisonguard
    metrics_path: /metrics
    scheme: http
    authorization:
      credentials: ${SERVE_API_KEY}   # -> X-API-Key 头
    static_configs:
      - targets: ["serve:8000"]
```

- **核心指标**（`poisonguard_*`，全部手写无依赖）：

| 指标 | 类型 | 看什么 |
| --- | --- | --- |
| `poisonguard_http_requests_total{method,path,status}` | counter | 分路径请求量、5xx 突增 |
| `poisonguard_score_latency_seconds` | histogram | `histogram_quantile(0.99, rate(...[5m]))` 出 p99 延迟 |
| `poisonguard_score_texts_total` / `score_requests_total` | counter | 吞吐（text/s） |
| `poisonguard_batch_jobs_total{state}` | counter | 批处理 done/failed 比例 |
| `poisonguard_model_info{version}` | gauge | 各副本当前版本，**跨实例版本漂移告警** |
| `poisonguard_component_present{name}` | gauge | kNN/ngram/student 装配情况 |
| `poisonguard_uptime_seconds` | gauge | 实例存活时长（`up` 当主） |

- **推荐告警**（Prometheus rules 片段）：

```yaml
groups:
  - name: poisonguard
    rules:
      # 5xx 比例 >2% 且持续 5 分钟
      - alert: PoisonServe5xxHigh
        expr: sum(rate(poisonguard_http_requests_total{status=~"5.."}[5m]))
              / sum(rate(poisonguard_http_requests_total[5m])) > 0.02
      # p99 延迟超 500ms
      - alert: PoisonServeP99High
        expr: histogram_quantile(0.99,
              sum(rate(poisonguard_score_latency_seconds_bucket[5m])) by (le)) > 0.5
      # 副本版本漂移：model_info 出现 ≥2 个不同 version
      - alert: PoisonServeVersionDrift
        expr: count(count by (version) (poisonguard_model_info)) > 1
```

## 7. 审计在多实例下的取舍

- **默认**：每副本写各自的 sqlite（`/tmp/audit/audit.sqlite3`，容器内独立卷）——
  最简单、无锁竞争；合库时用 `recent()` 导出后按 `ts` 归并即可。
- **要单库**：把 `--audit` 指向共享存储（如 NFS/云盘上的一个 sqlite）。
  SQLite 写入是整库锁，量上来会串行化；`AuditStore` 已用 `timeout=30` + 写失败吞异常兜底，
  但**不要**在 QPS>几十且要严格审计的场合用共享单库 —— 换 PostgreSQL/ClickHouse，接口层包一层即可。

## 8. 上线检查清单

- [ ] 三件套（config / processed data / student.pkl）做成不可变 tag，全部副本同一 tag
- [ ] 所有副本 `/health` 的 `model` 字段一致（可用脚本对 LB 后每实例各 curl 比对）
- [ ] `/score` 打任意副本结果一致（拿同一批文本分别打 2+ 副本对比 flag）
- [ ] 鉴权开启时，Prometheus 抓取带 `X-API-Key`，Grafana 能看到每副本 `model_info`
- [ ] `/batch` 走 sticky 或 Redis 队列，轮询能稳定拿到结果（不 404）
- [ ] 只有 admin-node 暴露 `--admin-key`；LB 地址不对外协商命
- [ ] 审计：每副本独立文件可写；共享库时压测过并发写
- [ ] 滚动发布演练：摘流 → 重启 → 校验 → 接入，全程无 5xx 峰

## 9. 已知边界（多实例视角）

- 令牌桶限流是**每实例**的：N 副本 = 全局额度 ×N。要精确全局配额，在网关/Redis 层另做。
- `/stats` 是单实例统计；全局聚合靠 Prometheus 对每副本指标做 `sum()`。
- 批处理 job 的进程内淘汰（128 上限）只约束单副本；量级再上去请走路线 B。
- 编码器权重每副本各加载一份（约 400MB 内存）；`model_cache` 共享只省下载、不省常驻内存。
